#+TITLE: Selective generalized component construction

* Native composition

This advances the generalized-prototype future work. Computation expressions
(~dependency-analysis.ss~) infer dependencies from child expressions, including
presence observations and both conditional branches. Declaration sources
(~generalized-graph.ss~) support define/remove/set-base/support and reject cycles
or unsupported reads before construction. Builder and materialized caches
(~construction-cache.ss~) retain successes, source failures and real absences.

~StagedPublication.methods.construction<-cache~ specializes the existing model's
~.construct / .refresh~ hooks. The Boolean cyclic solver remains its default;
general component graphs require a valid DAG schedule. Cooking, typed generics,
negative watches, contracts and joint approval reuse one shared finish boundary.

* Reuse and invalidation

Reuse requires exact program/base identity and clean transitive dependencies.
Equal outputs or version labels cannot authorize reuse. Changed support/order is
conservative. A dependency-ordered pass materializes each shared node once; clean
slots never invoke a builder or resolver. Source capture uses direct lookup tables
for active keys while preserving latent code/base for later support edits.

An identical captured source retains its lookup and schedule in constant source-
level work (one private cache record and shared traces). Changed sources still
capture and scan supported keys. ~reschedule~ reuses checked order/reads when
support and every complete footprint agree; changed edges fall back to full
cycle/unsupported validation. Value/program invalidation is independent: a new
method body still rebuilds its cone even when its reads are unchanged. Private
transient tables reuse the standard hash library. Values, source objects and
callbacks must remain stable and pure. Open POO metadata and arbitrary extension
callbacks do not carry dependent kernel proofs. Extensions must declare their
reads; actual undeclared provider accesses are refused.

Accepted releases refresh generics from closed per-service inputs. Equal inputs
under the identical model retain exact warm certificates; changed inputs rebuild
only that generic, including registration and completed-candidate negative checks.
ContractFamily also projects descriptor inputs and retains wrappers with the same
executor, while revalidating current service support.
Calls retain the exact component cache and recheck the actual service-cache
successor. A refused release retains the identical previous version, including
its component values and warm service caches. External effects are outside this
value rollback contract.

* Shared settlement example

~examples/construction-workflow.ss~ reuses ConstructionWorkflow's fifteen keys:
input feeds freight/cover/audit, tax/risk merge at settlement, invoice/audit merge
at release, and the absence of blocked feeds total. It composes the existing C4
ServiceBundle and its quote/reserve/cancel metadata and negative-watch rules.

- Input 30: 15 evaluated, total 32.
- Invoice adjustment: 3 evaluated / 12 reused, total 41. Reservation, cancellation
  and guarded Bank quotation all capture the revised component values.
- Shared input 60 after that adjustment: 11 evaluated / 4 reused, total 67.
- Discount presence change invalidates risk and all dependent joins.
- Policy-only repricing: 0 evaluated / 15 reused, even with a builder refusing all
  nodes. The family and contracts still rebuild and undergo joint approval.
- Cycles, builder refusal, blocked capability, forbidden dispatch and late joint
  refusal cannot publish a mixed version.

The component arithmetic aligns with the Lean settlement example. Existing
Scheme C4 quote policies are reused; full dependent-type or quote-policy parity
is not claimed.

* Stable and dynamic joint approval

The native model's ~.readmit~ method defaults to full ~admit~. ServiceBundle
specializes it to ~cache-admit~: every new publication runs all three business
probes, release/ceiling checks and the budget; each call checks the actual
successor budget. Methods, contracts, cooked view and policy remain immutable
through dispatch-cache insertion. Stable probes therefore retain their meaning.
Custom overrides must justify every omitted check; an arbitrary cache-dependent
or effectful predicate must continue to use full admission.

Differential controls run identical cold/hit/cross-service calls under full and
factored approval, comparing results, refusals and all cache sizes. A second
service exceeding the joint budget still refuses without leaking tentative state.
Schedule controls cover equal footprints with new bodies, changed edges, cycles
and unsupported reads. Lean's ~Scheduled.rebase~, ~Cache.retain~, family definition
and observation preservation, and ~Snapshot.invokeRetaining~ state the respective
proof obligations. They do not constitute compiler/runtime refinement.

Native same-process controls include full/retained scheduling, recaptured/same-
source zero-builder preparation and full/factored cold/warm joint admission.
Release measurements include construction, generic rebuilding, contract binding
and full fresh approval. These finite observations do not prove universal speed.

* Selective service-family revision

~GenericFamily.Projection~ captures a finite immutable input value per generic;
~expand~ constructs its closed policy/view environment. Native
~methods.refresh<-projection~ derives build/prepare/refresh using those inputs
and the existing seed/method/watch callbacks. Source/model identity is mandatory.
A changed source reconstructs everything even when input values compare equal.
The private family carries warm certificates and source contexts; only invoke
can create a warm successor. Context/prototype values and callbacks remain pure
and stable. Context equality is an optimization premise, not a version stamp.

The staged model now calls family prepare/refresh in its existing atomic chain.
Unchanged entries share their original cache; the service table is copied only
on the first changed entry. New generic registration/negative refusal or late
joint refusal returns the identical old version. Cold construction uses the same
projected environments. Default models conservatively reconstruct all services.

ServiceBundle projects quote capacity/price/extension flags, reserve
capacity/release/shift/signature, and cancel invoice/shift/negative flags. A price
revision rebuilds quote while retaining exact warm reserve/cancel objects. An
invoice revision rebuilds cancel only. A no-op revision retains all three. Joint
cache approval counts retained warm caches; tightening a limit can refuse even
when no generic was rebuilt. Negative assumptions are checked on every changed
generic. Changing the approval program falls back to full approval.

Stable quote/cancel business conclusions can transfer only from the identical
admission source, identical actual service and identical contract descriptor
(absence included), with matching expected view inputs. Current ceiling/release
and exact successor cache budget are always checked. Reservation contracts/wrappers now retain through ContractFamily when their
source/inputs and executor agree; exact service/contract identity permits retaining
the reservation business conclusion as well. Arbitrary custom admission
or contract changes cannot inherit this shortcut.

Runtime controls compare projected and direct constructors over 36 view settings
and six actual calls each, preserve sibling cache identity, and test changed code,
new budgets, changed admission, negative conflicts and atomic refusal. Native
matched release controls compare selective versus forced cold preparation for
no-op, price-only and invoice-only revisions. Complete 400-row data remains in
ignored build output. Lean has Source.asModel/projection, Certified.transport,
Partial.refresh_retained, and stageRefresh/publishRefresh with refusal identity.
This is executable alignment with explicit premises, not compiler refinement.

* Contract-family preparation

~contract-family.ss~ supplies native ~Source.~ with keys/project/construct and
derived ~.prepare / .refresh~. Only projected inputs reach construction. Source
identity changes force reconstruction; equal names/results cannot authorize reuse.
Every requested key is checked against current service support before projection
or construction; duplicate names and invalid descriptors refuse preparation.

Private contract and invoker tables share unchanged entries, with independent
copy-on-write on first descriptor/binding change. An executor change reuses the
descriptor but binds a new wrapper; key removal rebuilds finite support and cannot
leave stale invokers. Wrappers receive the current publication snapshot as an
argument and resolve services there, including freshly replaced generics. Custom
legacy contract callbacks fall back to ordinary preparation rather than being
ignored by the projection mixin.

ServiceBundle projects the reservation contract on capacity. Price/invoice-only
revisions retain both descriptor and wrapper. Existing joint admission transfers
the reserve observation only from the same admitted source and same actual
service/contract identities with unchanged expected capacity. New ceilings,
release conditions and the actual cache budget are still checked. Normal calls
always enforce input/output/relational predicates; retained wrappers never bypass
checks. Contract removal, changed constructor, missing service and late refusal
retain the previous version on failure. Source exceptions remain distinct from
business error values through the existing metadata wrapper.

Native tests count actual construction/wrapping/probe calls, exercise input and
logic refusal, replacement services through retained wrappers, independent
executor rebinding, contract add/remove, duplicate/missing keys and legacy
contract overrides. Lean ContractFamily certifies origins/bindings and exact
zero-build/zero-bind retained traces, current-state invocation, missing-service
refusal and atomic joint refusal; its reserve/cancel example changes invoice
while retaining reserve. Matched native phases isolate cold/retained preparation,
changed inputs, rebind-only work, and complete no-op/price releases with cold
versus retained contracts. These are finite observations, not verified Scheme
allocation/compiler/runtime claims. Complete data/binaries remain ignored outputs.

Contract release pairs use 128 operations on both sides after an initial 8-op
natural-GC price regression. The concise performance summary retains that
negative observation; initial data/log/source and final measurements stay ignored.
The follow-up changed batch size only, preserving production source and all
compile/time/heap bounds. It does not establish a universal performance guarantee.
