* First-image validation: measured boundary and rejected representation policy
A macOS follow-up separated two =fcntl= operations used by dyld. A temporary
=std/ffi= probe in the actual released Gerbil process, against three fresh
project images, measured successful signature registration
(=F_ADDFILESIGS_RETURN=) at 0.109--0.179 milliseconds and successful library
validation (=F_CHECK_LV=) at 0.421--0.475 seconds per image. A fresh-image probe
outside the tool sandbox still spent 0.626 seconds in validation. This locates
an operating-system validation boundary; it does not identify its underlying
policy service or attribute the entire entry's residual wall time to that call.
No security policy, signing, extended-attribute or compiler changes are retained.
Apple's [[https://github.com/apple-oss-distributions/dyld/blob/main/dyld/Loader.cpp][dyld Loader source]] distinguishes these operations in image mapping;
the host measurements, rather than that upstream source, establish these times.

Gerbil already caches canonical module identities, initialization failures and
load order. =module-action= retains that loader and resolves current bindings
at execution. In a three-module trace, six distinct phase/runtime images were
mapped once each. First import of freshly built images took 5.50 seconds, versus
0.32 in a fresh process reusing the same files. This is not evidence of repeated
initialization of the same identity, nor a measurement of every full-run load.
Another one-second sample during the final candidate run contained 379/837
main-thread samples under =dlopen=, including 348 under =notifyDebuggerLoad=.
Sampling can itself affect image notification; this observation is not assigned
as the cause of the preceding unobserved wait or the whole run.

A candidate selected Gerbil's existing Scheme fallback for generated canonical
forwarders containing only literal =load-module= calls. Runtime/macro phase
bodies, interfaces and static objects stayed compiled. Its small independent
import experiment improved from 1.52 to 0.25 seconds, but the complete entry
failed to reproduce a consistent benefit. It is rejected: no generated-source
rewriter, new loader/cache, extra build callback or test-package wrapper is
retained. Standard =defbuild-script= and =gerbil clean/build/test= still own the
entire compilation, freshness and execution lifecycle.

* Reproduction and attribution
Use an empty GERBIL_PATH outside the checkout for a cold run; repeat the exact
command with the same path for a warm run. Keep the release and worker count
fixed and retain /usr/bin/time -l output, standard make progress and exit status.
The driver emits actual stage starts/ends and source-admitted cache hits. Full
logs, traces, compiler artifacts and archives remain outside Git.

The historical t/build-benchmark.ss collector recorded macOS process parentage and
timestamped output in Scheme data. Sampling runs diagnose worker overlap;
unwrapped runs qualify wall time. Sampling cannot identify very short processes
or prove continuous worker occupancy. A GSC interval includes its C compiler and
linker descendants. GCC -pipe permits C compilation and assembly to overlap;
clang -cc1as is assembly, not a linker. Inclusive intervals must be unioned rather
than blindly added. Import spans combine resolution, interface reading and
expansion; they must not be relabeled pure macro-expansion time.

The bounded-batch completion receipt establishes feasibility, not an end-to-end
speedup ratio. Complete cold/warm measurements and exact-revision CI are required
before publishing a complete-workflow performance claim.

* Bounded failure recovery and current macOS cold controls
The standard make implementation admits a gxc target from its SSI and static
Scheme outputs. These precede completion of its deferred backend object. A killed
backend can therefore leave metadata which makes the next make appear current
although its runtime object is old. A zero exit from that metadata-only warm
control is not runtime acceptance.

All =just build= targets now use the existing bounded stage boundary. After a
failed compiler process group is reaped, that boundary invokes the selected
standard =clean= request, retaining its target/output and discarding compiler
options, then rethrows the original failure. There is no new scheduler, worker
budget, environment variable, artifact journal or hand-written file invalidation.
=defbuild-script= and =std/make= continue to own cleanup, dependencies and reuse.
A failed cleanup stops later compiler admission and retains both causes. A kill
of the supervisor itself is outside this recovery guarantee; use =gerbil clean=
before rebuilding after such an interruption.

the same module successfully with the standard macro. Production compilation
