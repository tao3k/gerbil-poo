* What the historical 60.563us does and does not establish
The previous source's +84.156us CPU / +23.594us GC / +60.563us residual remains
in context-binding-summary.org with its original receipt/source identity. Both
old Reader strategies there used qualified carriers. Descriptor/cache work was
COMMON to both: it cannot by itself explain that particular paired difference.
Residual CPU includes allocator/cache/memory effects and is not pure method CPU.
The precise historical difference is not retroactively assigned to slot caches,
GC or any single cause. Current phase controls locate a large removable COMMON
cost and test a representation intervention on fresh matched processes.

At the source level each raw method was a full POO Contribution. First qualifier
or body selection prepares its object/slot caches; even item-only cooking scanned
the same list for around and item groups. Compact storage retains only the
method closure. Both strategies still create fresh closures/current observations.
Warm item lookup and warm dependency cooking are separate controls: they cannot
stand in for a cold complete factory.

* Fixed native design
Before measurement: THREE complete final-source runs, each 624 children:
13 phases, two regimes, four rounds, three pairs, two sides. Existing shared
native paired I/O, ABBA, exact SAME-procedure A/A, fresh child per side, common
setup/warmups of all four controls. No build/test overlap. Fixed limits remain
90s AOT, 90s per study, 20s per child, 1GiB heap. No selected best run or pooling.

Both complete factory sides use current public report binders, the SAME fixed
field-list projection and output oracle. Each call includes preparation, binding,
raw finite construction, demanded cooking and public selection. The declaration
graph is warm common setup, not first module load or cold C3-node generation.
=preparation= constructs a fresh snapshot and inspects provenance; =binding=
constructs the same context reader without executing it. =construction= executes
two raw stages and real shape/audit/current metadata selectors, not method bodies.
=cooking= prepares a new final interface over an untimed precomputed raw value:
dependent self promises AND item caches are warmed before timing. This excludes
cold dependency construction, explicitly. Phase timings must NOT be summed.

=item-construct= compares qualified carrier construction/provenance with the
already available method function. =item-cold= constructs a descriptor and makes
its FIRST body lookup/invocation; =item-warm= uses a preconstructed warmed body
cache. These are API work comparisons, not artificial forced allocation. They
do not separately identify C3 versus slot-table subcosts. =factory-history= runs
64 real qualified observations before common warmups; natural never forces GC.
Collected only requests premeasurement GC; neither regime equalizes heap shape,
addresses, page residency or complete GC history. Matching prefix counters are
not matching histories. Bytes are admitted only on BOTH GC-free nonnegative sides.
